# Load Test Results

Generated by `scripts/loadtest.py` against the gateway (port 18000 of a parallel Docker stack), 20 concurrent
connections for 30 s per round. Request mix: 40% product listing, 20% product by slug,
10% categories, 20% stock, 10% order creation (with `Idempotency-Key`). The full result is in
`docs/loadtest-result.json`.

How to reproduce:

```
backend/gateway/.venv/bin/python scripts/loadtest.py --base http://localhost:8000 --duration 30 --concurrency 20
```

- **A1 to A3:** gateway limits raised (`RATE_LIMIT_PER_MINUTE=100000000`) to measure capacity.

- **B:** default limits (600 per minute per route, 120 for `ordering`), with the Redis buckets reset beforehand.
  About 58.95% of requests received a 429 with `Retry-After`, and **none** produced a 5xx error:

## Interpretation

- Zero 5xx errors and zero network failures in every round, including under the rate limit.
- The gateway runs a single uvicorn process and sat near 100% CPU during the load: it is the bottleneck
  of this measurement, not the catalog. Scaling out (more replicas) is safe because the limit lives in
  Redis and is shared.
- The per-route limit works independently: `ordering` (120 per minute) starts refusing long before
  `catalog` and `inventory` (600 per minute each).

## Caveats

- Shared machine: during the rounds the host load average went above 30 (other containers and
  processes), so the variation between A1, A2, and A3 (109 to 151 req/s) is more environmental noise than a
  property of the system. The numbers are for comparing versions on the same machine, not absolute capacity.
- Client and server share the same host and compete for CPU.
- The measured stack has catalog, inventory, ordering, payments, and ledger. Notifications and assistant
  were not running.
